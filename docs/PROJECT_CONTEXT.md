## 项目目标

用户安装 WorkBuddy Skill 后，可以先探索麦当劳隐藏吃法的图片。即使不知道具体餐品名称，也能通过随机推荐、类别和口味逐步选到想吃的组合。选定后，Skill 解释可靠配方，再在用户要求时调用麦当劳官方 MCP，把组合映射成当前门店可核实的餐品清单。

Skill 的价值是资料整理、探索、配方拆解、证据判断、差异解释与流程编排；MCP 提供门店、商品和价格等基础查询。民间组合不是官方「隐藏商品」，组装通常由用户拿到餐品后完成。

## 2026-10-25 本轮授权：阶段触发与安装同步

用户要求统一源码和 WorkBuddy 安装版，修复选号／购买阶段触发，并确保修改的口味、份数在后续步骤保留，完成后由用户测试。选号只加入备选；用户明确要求配置、核价或准备购买时才统一核菜单、核券、核价。回到探索保留配置，明确清空或重新开始才清除；同一会话复用一份购买计划。此次授权包含本地代码修复、验证、打包与安装同步，不包含实际领券、下单、支付或公开发布。

## 已确认的需求

- 重点服务「我不知道想吃什么，想看看」；不能只服务已经知道某个吃法名称的人。
- 用户关注资料覆盖面，但不能声称收齐「所有」隐藏吃法。需按来源、变体、地区与时间整理，避免标题不同就重复计数。
- 需要图片支持：随机给一张；按「薯条相关」等意图给多张；选图后再安排决策和清单。
- 实际使用宿主是 WorkBuddy；明确包括 WorkBuddy 手机 App。桌面本地浏览器成功不能替代安装后或手机验收。
- 手机 App 中用户测试旧 HTML 只看到了代码，且打开 HTML 会阻挡连续交流。这是用户报告的失败样本，不应当继续把 HTML 当已完成的主流程。
- 希望两天内能做出可演示、有实际价值的参赛版本。优先完整跑通有限场景，不增加未经验证的第三方 API 依赖。
- 2026-10-24 用户指定 `mcd-mcp-event` 作为后续开发项目。

## 讨论路径与取舍

| 方向 | 讨论／证据 | 当前处理 |
| --- | --- | --- |
| 跨麦当劳、抖音、大众点评比价 | 用户真实痛点是反复查券、看团购再比较；已研究麦麦智能管家的美团联盟实现 | 暂不依赖；个人准入和自己的真实商品查询未跑通 |
| 个人申请第三方 API | 用户没有联盟 AppKey/Secret；申请入口需本人登录，用户当时无法登录 | 未代替用户完成申请；不能说个人绝对不能申请，也不能说已获得权限 |
| 省钱／拼单／验单 | 基于 101 项历史样本，提出过「麦麦照单比」「拼单不吃亏」「麦麦验单员」 | 候选讨论，未作为当前产品主线 |
| 营养／卡路里 | 已查看多个预算、热量、饮食计划竞品，用户要求避免同质化 | 可作为选定组合后的可选信息，不以泛化低卡配餐作为核心差异 |
| 隐藏吃法 | 用户选择「资料全面 + 图片探索 + 选后拆解」 | 当前主线 |
| HTML 图库 | 包内嵌图已通过桌面 WorkBuddy 预览；手机样本失败 | 保留可选完整浏览入口，主交互重新验证 |
| PNG／四格图 + 编号 | 最新建议，适合保留聊天连续性 | 尚未实现、尚未在手机验收，不写成用户已选定的最终方案 |
| 内联卡片／MCP Apps | 有竞品源码和官方桌面能力说明 | 作为技术候选；手机支持未证明，不作为两天版本前置条件 |

## 拟议体验与最小范围

1. 用户说「随便看看」：从真实收录资料里抽一张成品图，附稳定编号、名称和一句口味描述。
2. 用户说「薯条相关」：给 3～4 个候选，优先测试四格 PNG 或多图消息；每个可见序号映射到稳定 ID。
3. 用户说「换一批」「想吃咸的」：保留已看记录，按类别／口味调整，不进入点单。
4. 用户选定：查规范 ID、来源和配方状态；只有封面就先核来源，不脑补配方。
5. 用户要求「帮我配置／准备点」：确认必要的门店、取餐方式和时段，查菜单与详情，映射原料并核价。
6. 输出已匹配餐品、未知项、原版与替代版差异；当前默认不创建订单。

上述随机、筛选和四格交互是产品建议，不代表现有公开 Skill 已具备。

## 资料模型要求

- 稳定 ID 和别名；当次可见编号与 ID 的映射，避免「第 2 张」在换批后错配。
- 吃法名称、类别、口味、原料、数量、步骤、操作难度、地区和时段限制。
- 每项来源 URL、作者／机构、日期和采集日期；报道转述与直接核验分开。
- `cover_only`：只有封面，不能有臆造配方；`reported_recipe`：来源明确描述了步骤，未知数量保持未知。
- 图片区分成品、过程、原料、拼图、插画和可能 AI 示意；记录来源与权利状态。
- 原料与实时门店 SKU 映射单独保存查询上下文和时间，不固化为永远可售。
- 相似组合、口味变化与造型变化建关联；来源重复、图片重复不能扩大独立配方数。

## 尚未决策的问题

- 同一张本地 PNG 在手机 App 正文、图片产物卡中的实际表现。
- 是否能实现真正的点击选图回传，或以编号／语音选择作为主交互。
- 手机「云端工作」和「连接电脑」两种模式的安装资源与交付差异。
- 首批正式素材的选择、公开使用依据和成品图覆盖率。
- 最终命名、公开版本、真实菜单映射演示样本和比赛发布／报名。

先完成图片交互最小验收，再确定图片展示的实现路线；本次归档没有实现上述新功能。

## 2026-10-24 新增的收集约束

用户进一步要求：收集的隐藏吃法必须能关联具体商品名，或有充分依据可靠识别；核心原料不能是时令食品，并且配方有可操作性。对应图继续要求是吃法本身，优先实拍。执行标准见[COLLECTION_STANDARD.md](COLLECTION_STANDARD.md)。这是资料准入规则；当前门店及价格仍需在实际配置时核查。

## 地区商品名处理补充

用户同意将原来的“当前缺项”拆成配方、商品核验与非时令等独立项目，并要求台湾等地区叫法改用大陆商品名。资料需保留原名、标准名和对应依据；无法等价对应的不得更换食材，应保留待核或单独建立替代方案。
